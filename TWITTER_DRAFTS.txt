[2026-09-26] Post 11 — v3: real ms-latency, and a real reality check
===============================================================
Two updates.

1) sys1 finally hits the speed the whole idea was built around. Swapped
the causal-chat-model-plus-logits approach (v1/v2) for a small
non-autoregressive encoder + decision head (Laya's actual architecture,
not a retrofit): one batched forward pass, no chat template, no
generation.

Same CPU, no GPU, measured end to end:
v1/v2 (Qwen 0.5B/1.5B via chat template): seconds per decision
v3 (22M-param encoder): 34.6ms average, Snake at 2.7ms/tick

It's not just faster -- it's MORE accurate on our own held-out data too
(87.1% vs 85.9%, Brier 0.18 vs 0.21). The architecture retrofit was
costing us on both axes.

2) Then I found out how Jev and Laya actually get benchmarked --
public datasets (Luni/laya-jev-benchmark: PhishNChips phishing emails,
LocalLLaMA/typed-decisions agent-trace risk assessment) -- and ran sys1
through the exact same tasks instead of just our own eval set.

Reality check: 87% on our own data, 37% on the public agent-trace
benchmark, on a domain (agent risk/urgency judgment) nothing like our
training data (support tickets, complaint urgency, frustration
detection). Same real model, same real pipeline, just tested honestly
on someone else's task instead of our own.

Ran the bigger causal-LM version (v1/v2, 1.5B) through the same
benchmark for comparison: 22.7% accuracy, ~4.4s per decision. The small
22M-param encoder beat a 68x-larger model on unseen data AND did it
~130x faster. Bigger ≠ better when neither has seen the domain --
architecture and training objective mattered more than parameter count
here.

Good news: the speed and the training method both work, on data outside
what either model has seen. The gap is data coverage, not architecture,
and now we know exactly where it is instead of guessing. Next: train on
the domains these benchmarks actually test, and post the real
before/after.

[2026-09-23] Post 9 — the bug wasn't the model, it was asking it to remember
===============================================================
Had sys1 playing Snake (state -> Choice -> direction, one call per tick).
It kept zigzagging into itself instead of heading to the food. Looked
like a broken model. It wasn't.

Every tick was judged fresh, with zero memory of the previous tick. So
if it lined up with the food on one axis, the NEXT tick had no idea that
alignment was worth protecting -- it would casually undo its own
progress. Small model, no memory, no plan. Exactly what you'd expect.

Fix wasn't "train harder" -- it was architectural: move memory into the
game engine, not the model. Once you commit to closing the gap on one
axis (x or y), the correct move along it is 100% deterministic -- no
judgment needed, so don't ask. That commitment now lives in
game.focus_axis, code-owned, persists tick to tick. The model only gets
asked two genuinely ambiguous questions: which axis to prioritize when
both are open, and what to do when the planned move turns out unsafe.

Before: dies fast, doesn't reach food, visibly incoherent.
After (same 0.5B model, same everything else): 3 foods eaten, alive at
60/60 ticks, and the model was only needed on 8 of those 60 ticks (13%).
Most of the game now runs as instant deterministic code -- the model
shows up exactly when there's a real decision, not every single frame.

Screenshot: live run in the sys1 Streamlit UI, showing the grid plus the
"model calls X/Y" counter tick by tick.

[2026-09-22] Post 1 — v0 announcement (logit-based judgment engine)
===============================================================
Building a tiny "System One" model from scratch — inspired by @[TypeSafe]'s
Jev. Not a chatbot: it makes typed judgments (pick one of N, yes/no, score
1-5) with real calibrated probabilities.

v0 (today): zero-shot logit scoring on a 0.5B open model, CPU only, no
training. Reads probabilities straight from next-token logits over a
constrained answer set instead of asking the model to "say" a confidence
(LLMs are bad at that).

v1 (next): LoRA fine-tune on free Colab GPU.

Building in public, will post the repo as it lands.

[2026-09-22] Post 4 — v1 LoRA fine-tune results
===============================================================
sys1 v1 is in. Fine-tuned the 0.5B base model with LoRA on ~520 real
examples (free Colab T4 GPU, a few minutes of training) and measured it
on 91 held-out examples the model never saw:

accuracy: 23.08% -> 59.34%
Brier score (calibration error, lower = better): 1.16 -> 0.55

More than 2x the accuracy and roughly half the calibration error from a
few minutes of free-tier fine-tuning on real (not synthetic) data. Same
tiny 0.5B model, same logit-based probability extraction, just better
weights. Next: more/bigger training data, then a bigger base model.

[2026-09-22] Post 5 — data scale-up, same 0.5B model
===============================================================
Tripled the training set (600 -> 1600 real examples, same public-dataset
sources, no synthetic data). Same 0.5B model, retrained:
accuracy 59.34% -> 63.07%, Brier score 0.55 -> 0.477.
Smaller jump than the first fine-tune (expected — most of the "free
lunch" was going from zero-shot to any fine-tune at all), but still a
real gain from data alone. Next up: same bigger dataset, but on a 1.5B
base model instead of 0.5B.

[2026-09-22] Post 6 — 1.5B model beats data scale-up
===============================================================
Same 1600-example training set, swapped the base model from 0.5B to
1.5B. Result: accuracy 63.07% -> 72.20%, Brier score 0.477 -> 0.35.

Full progression so far, same held-out eval each time:
0.5B zero-shot:        23.08% acc, Brier 1.16
0.5B + 600 examples:   59.34% acc, Brier 0.55
0.5B + 1600 examples:  63.07% acc, Brier 0.48
1.5B + 1600 examples:  72.20% acc, Brier 0.35

At this scale, going from 0.5B -> 1.5B params bought more than tripling
the dataset did. Small model, small free-tier GPU, real measured gains
at every step. Next: try 3B, and/or grow the dataset further to see if
the bigger model has more headroom to use it.

[2026-09-22] Post 7 — actually training for calibration, not just accuracy
===============================================================
Realized v1 was cheating a bit: plain SFT (next-token cross-entropy over
the whole vocab) makes the model more likely to say the right answer, but
nothing in that loss cares whether the resulting probability is honest.
Jev's own training (per TypeSafe's docs) is "RLCD" -- reinforcement
learning FOR calibrated decisions, optimizing the probabilities
themselves against real outcomes.

Our "decision" is a single differentiable softmax over a few candidate
letters -- no need for full RL/reward-model machinery to get the same
property. v2 trains with plain gradient descent directly on that exact
distribution (masked cross-entropy over just the candidate logits), which
for a one-step decision like this IS the calibration objective. Also
found and fixed a bug while building this: training data for the Score
primitive was using the wrong prompt header vs inference, so it was
learning a slightly different task than it was evaluated on the whole
time. Numbers next post.

===============================================================
[2026-09-22] Post 8 — calibrated training beats plain SFT, same model/data
===============================================================
Same 1.5B model, same 1600-example dataset, only the training objective
changed:

v1 (plain SFT, whole-vocab cross-entropy):     72.20% acc, Brier 0.35
v2 (direct calibrated-decision training):      85.89% acc, Brier 0.21

Whole-vocab next-token loss spends almost all its gradient on tokens
that were never even candidate answers. Training directly on the exact
softmax-over-candidates distribution the engine reads at inference puts
100% of the signal where it matters. Biggest single jump of the project
so far, and it's the training method that's actually closest to how
Jev itself is trained (RLCD -- optimizing the decision, not just next
tokens) -- just without needing full RL for a one-step decision.
